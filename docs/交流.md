以下是对我们本次关于“Vue3 混合架构（App/PC 宿主嵌入）项目的 UI 自动化测试”对话交流的全面总结。

1. 核心背景与痛点

• 技术栈：前端采用 Vue3 开发，分别通过 Iframe、移动端 WebView、PC 软件 WebView2 被多端宿主嵌入。
• 交互难点：项目极度依赖宿主环境，通过宿主主动注入登录信息/Token 完成初始化，且前端需要调用封装的 JS-SDK 来触发宿主原生组件或调用跨端组件。
• 团队现状：团队技术栈最熟悉 JavaScript/TypeScript。

2. 自动化 UI 测试方案对比与选型

我们针对该架构分析了 3 种测试演进方向：
• 方案一：独立 Web 隔离测试（Mock 宿主）：在纯网页端伪造 SDK，速度极快，维护成本低，但无法覆盖原生层 Bug。
• 方案二：真宿主环境 E2E 测试：使用 Appium/WebDriver 操控真实客户端，还原度最高，但环境配置极度复杂、执行慢且极其不稳定。
• 方案三：分层分段测试（混合方案 - 🌟最推荐）：90% 的业务 UI 逻辑通过 Playwright 结合 Mock SDK 进行极速验证，10% 的跨端交互边界通过接管真实宿主进行专项验证。

3. 技术痛点攻克：JS-SDK 双向通信自动化


场景 A：前端主动调用 SDK 获取数据（如 Get 方法获取登录信息）

• 解决方案：在 Playwright 启动时通过 page.addInitScript() 提前注入 Mock SDK。将 SDK 的 Get 方法改写为返回一个 Promise，以此完美模拟真实的异步跨端通信，并返回预设的 Mock 登录数据。

场景 B：前端调用 SDK 触发宿主组件（如扫码、弹窗）

• 解决方案：利用 “白盒化对账机制”。在 Mock SDK 内部建立一个全局数组（如 window.__SDK_CALL_LOGS__）拦截并记录 Vue3 的每次调用。测试脚本中通过 page.evaluate() 读取该数组，断言前端传给原生的 JSON 入参格式与字段是否完全正确。

场景 C：宿主主动向网页推送事件（反向通信，如网络断开）

• 解决方案：在 Playwright 测试脚本运行的中途，利用 page.evaluate() 动态创建并抛出自定义 Web 事件（如 new CustomEvent('hostMessage')），人为“伪造”宿主的推送动作，从而稳定验证前端的容灾或响应 UI。

4. 真实宿主环境下的接管与联调（如何连本地测试）

当项目已经加载在真实的测试环境或客户端中时，可以通过 CDP（Chrome 开发者工具协议） 实现本地脚本的直接接管：
• PC 软件（WebView2/Electron）：启动软件时附加 --remote-debugging-port=9222 参数，Playwright 使用 chromium.connectOverCDP() 连入，注入 Mock 脚本后执行 page.reload() 刷新生效。
• 移动端 App（模拟器/真机）：App 开启 WebView 调试权限后，在本地终端利用 ADB 建立端口映射（adb forward tcp:9223 localabstract:webview_devtools_remote），随后用 Playwright 接管 9223 端口。

5. 高 ROI 替代方案：脱离宿主的前端工程化打包测试

如果不想依赖或接管复杂的宿主环境，可以通过调整前端的构建与运行方式实现“自给自足”：
• 方案一：环境变量打包（编译时注入）：配置 .env.automation 环境变量，利用 npm run build:auto 打包出专门给自动化测试使用的网页包。当网页检测到 VITE_IS_AUTOMATION_TEST=true 时，在内部自己长出一套 Mock SDK。该方案安全度高，不污染生产环境。
• 方案二：URL 参数激活（运行时注入）：直接复用现有的测试环境网页，在前端代码中加入拦截逻辑。Playwright 测试时直接访问带有后门参数的地址（如 ?__automation_test__=true）即可动态激活 Mock 状态，维护便利性极高。
