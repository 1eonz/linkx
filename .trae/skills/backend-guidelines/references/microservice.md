# 微服务架构开发维护规范

> 参考: Martin Fowler 微服务原则、Spring Cloud 官方文档、阿里巴巴微服务实践

## 一、服务拆分原则

### 1.1 核心原则

| 原则 | 说明 |
|------|------|
| 单一职责 | 每个微服务只负责一个业务领域，只有一个引起变化的原因 |
| 高内聚低耦合 | 服务内功能高度相关，服务间依赖最小化 |
| 数据自治 | 每个服务拥有独立数据库，禁止跨库连表查询 |
| 业务域对齐 | 按 DDD 限界上下文拆分，而非技术层拆分 |
| 独立部署 | 每个服务可独立开发、测试、部署、扩展 |
| 渐进式拆分 | 先模块化 → 垂直拆库 → 非核心服务 → 核心服务，禁止休克式拆分 |

### 1.2 拆分反模式（禁止）

- 按技术层拆分（如: 一个服务只做 DAO，一个只做 Service）
- 共享数据库（微服务共享数据库 = 分布式单体）
- 过度拆分（CRUD 级别的微服务，增加通信开销）
- 循环依赖（A 调 B，B 又调 A）

### 1.3 拆分验证标准

- 修改一个服务的代码，不需要修改其他服务
- 修改一个服务的数据库表结构，不影响其他服务
- 一个服务宕机，不影响核心交易链路
- 两个服务可以独立部署，无时序依赖

## 二、服务治理

### 2.1 服务注册与发现

规则:
- 服务启动时必须向注册中心注册，优雅停机时主动注销
- 服务名必须全局唯一，命名规范: `{业务域}-{服务名}`（如 `user-service`、`order-service`）
- 注册中心集群部署，避免单点故障

> 各项目注册中心选型（agent/server 用 Nacos、ccmd 用 Nacos/Zookeeper）见 `.trae/rules/backend.md` §7。

### 2.2 API 网关

- 所有外部请求必须通过网关，服务间内部调用可直连
- 网关职责: 路由转发、鉴权、限流、熔断、日志监控

> 各项目网关实现（agent/server 用 crs-gateway、ccmd 用 cloudcmd-gateway）见 `.trae/rules/backend.md` §2、§3。

### 2.3 配置中心

- 所有配置必须通过配置中心管理（Nacos），禁止硬编码
- 敏感配置加密存储
- 多环境隔离: dev / test / staging / prod
- 配置变更支持动态刷新，无需重启服务

## 三、服务间通信

### 3.1 通信方式选择

| 场景 | 推荐方式 | 说明 |
|------|----------|------|
| 同步查询 | HTTP/REST (OpenFeign) | 简单直接，适合查询类 |
| 高性能 RPC | Dubbo/gRPC | 适合内部服务间高频调用 |
| 异步解耦 | 消息队列 (RocketMQ/RabbitMQ) | 适合事件驱动、削峰填谷 |
| 广播通知 | 消息队列 Topic | 适合一对多通知 |

### 3.2 通信规则

- 服务间调用必须设置超时时间（连接超时 + 读超时）
- 禁止同步调用链超过 3 层（A→B→C→D 禁止）
- 跨服务调用必须携带 traceId，用于链路追踪
- 优先使用异步通信降低耦合

## 四、容错与韧性

### 4.1 熔断

- 外部依赖和跨服务调用必须配置熔断器
- 熔断条件: 错误率超阈值 / 慢调用比例超阈值 / 持续超时
- 熔断后返回降级响应，而非抛异常

> 各项目熔断方案（agent/server 用 Resilience4j、ccmd 用 Dubbo Mock/Sentinel）见 `.trae/rules/backend.md` §7。

### 4.2 限流

- 网关层: 全局限流，保护系统整体
- 服务层: 单服务限流，防止过载
- 接口层: 热点接口限流，防刷

限流策略:
- QPS 限流: 限制每秒请求数
- 并发限流: 限制同时处理请求数
- IP 限流: 限制单 IP 请求频率

### 4.3 降级

- 核心链路: 降级为缓存数据 / 默认值
- 非核心链路: 直接跳过（如推荐、统计）
- 降级策略必须提前定义，不能临时决定

### 4.4 重试

- 幂等接口才允许重试
- 重试次数 ≤ 3 次
- 重试间隔使用指数退避
- 非幂等接口禁止自动重试

### 4.5 超时控制

> 各层级超时数值（网关/Feign/Dubbo/数据库/HTTP Client）见 `.trae/rules/backend.md` §8。
> 通用通信规则（连接超时 + 读超时、调用链不超过 3 层、traceId 透传）见本文 §3.2。

## 五、分布式事务

### 5.1 原则

- 优先避免分布式事务（通过业务设计规避）
- 优先使用最终一致性，而非强一致性
- 禁止使用 `@Transactional` 跨服务传播

### 5.2 方案选择

| 场景 | 方案 | 说明 |
|------|------|------|
| 可补偿操作 | TCC | Try-Confirm-Cancel，适合资金类 |
| 最终一致性 | SAGA | 适合长流程业务编排 |
| 可靠消息 | 本地消息表 + MQ | 适合异步场景 |
| 强一致性 | Seata AT | 性能有损，仅核心交易链路 |

## 六、可观测性

### 6.1 三大支柱

| 支柱 | 工具 | 要求 |
|------|------|------|
| 日志 | Logback/Log4j2 + ELK | 结构化日志，含 traceId |
| 指标 | Micrometer + Prometheus | QPS/RT/错误率/资源使用率 |
| 链路追踪 | Micrometer Tracing + Zipkin/Jaeger | 全链路 traceId 透传 |

### 6.2 日志规范

> 日志的详细规范（级别/格式/脱敏/配置）见 [exception-logging.md](./exception-logging.md)

微服务日志额外要求:
- 所有日志必须包含 traceId、业务主键（跨服务追踪）
- 日志脱敏: 密码、Token、身份证号等必须脱敏

### 6.3 监控告警

- 核心指标: 可用性（SLA）、响应时间（P50/P95/P99）、错误率、QPS
- 告警分级: P0（5分钟响应）/ P1（30分钟）/ P2（2小时）/ P3（工作日处理）
- 每个服务必须提供健康检查端点（`/actuator/health`）

## 七、数据管理

### 7.1 数据库规则

> 数据库设计、索引、SQL、迁移脚本规范见 [database.md](./database.md)

微服务数据库额外要求:
- 每个微服务独立数据库，禁止跨库 JOIN
- 跨服务数据获取通过 API 调用，禁止直连其他服务数据库

### 7.2 缓存规则

> 缓存使用场景和详细规范见 [business-rules.md](./business-rules.md) 第七章

微服务缓存额外要求:
- 缓存 key 必须带服务前缀，避免跨服务冲突: `{服务名}:{业务key}`
- 缓存更新策略: Cache-Aside（旁路缓存）为默认方案
- 禁止缓存大对象（> 10KB），考虑压缩或拆分

## 八、部署与运维

### 8.1 容器化

- 所有服务必须容器化部署
- 基础镜像统一管理，定期更新安全补丁
- 支持 amd64/arm64 双架构

### 8.2 优雅上下线

- 服务启动后健康检查通过再注册到注册中心
- 服务下线先从注册中心注销，等待处理中的请求完成再停止
- K8s 配置: `readinessProbe` + `preStop` + `terminationGracePeriodSeconds`

### 8.3 灰度发布

- 新版本必须灰度发布，先小流量验证再全量
- 灰度策略: 按比例 / 按用户标签 / 按地域
- 必须支持一键回滚
